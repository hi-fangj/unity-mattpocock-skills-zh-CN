# 实施前冲突检查

把需求确认文档当作待验证的输入，不把它当作自动高于项目既有约束的事实。目标是让实现开始前只剩下一套明确、可追溯且没有关键矛盾的规则。

## 1. 收集对照材料

先从当前工作区和对话中找到需求确认文档。如果需求只有对话记录，先整理出可检查的条目，但不要擅自补充未确认的需求。

然后读取与本次功能相关的规则、约束和术语来源，至少检查：

- 根目录 `AGENTS.md`、`CLAUDE.md`，以及适用目录下的同名文件
- 根目录 `CONTEXT.md`，或由 `CONTEXT-MAP.md` 指向的所有相关 `CONTEXT.md`
- 根目录和相关 context 下的 `docs/adr/` 中仍然有效的 ADR
- 代码规范、架构规范、测试规范和项目专用开发说明
- 术语表、领域文档、README 中明确写出的不可违反规则
- 与实现边界直接相关的项目配置、生成代码约束和其他约束文档

只读取与本次功能相关的材料。对于多目录 context，按照 `CONTEXT-MAP.md` 和功能涉及的边界判断适用范围，不要把无关 context 的规则强行套用进来。

如果用户是在做定期维护而没有具体需求确认文档，则把当前仍有效的代码、测试和项目配置作为事实来源，审计文档之间的矛盾、重复、过期条目和放错目录的内容。先列出维护清单，再用选项逐项确认哪些内容应合并、移动、更新或废弃。维护模式不自动放行任何实现，完成后只报告文档状态。

## 2. 建立冲突清单

逐条将需求确认文档与对照材料比较，记录证据，而不是只给出结论。每条冲突至少包含：

| 字段 | 内容 |
| --- | --- |
| 编号 | 稳定的 `C1`、`C2` 编号 |
| 需求条目 | 需求确认文档中的原文或精确摘要 |
| 对照来源 | 文件路径和章节、ADR 编号或规则位置 |
| 冲突类型 | 需求冲突、文档互冲、术语冲突、疑似过期 |
| 影响 | 如果不解决，会改变哪个行为、边界、模块或测试 |
| 待裁决问题 | 需要用户决定的最小问题 |

区分真正的冲突和表面差异：不同措辞只有在会导致不同实现、不同术语含义或不同约束时才算冲突。对于已经被前置规则排除、不会改变实现的理论边界，不要重新制造冲突。

## 3. 用选项解决冲突

先展示冲突清单，再按依赖顺序询问。一次可以询问多个互不依赖的冲突，但每个问题都必须给出可直接选择的选项和推荐答案。不要只问“你想怎么办”，也不要把自己的推断伪装成既定规则。

```text
⚠️ C1 - <冲突标题>

需求确认文档写的是：<需求证据>
但 <来源文件与位置> 规定：<现有规则证据>
影响：<具体实现影响>

请选择：
A. <推荐选项>
B. <保留现有规则的选项>
C. <修改需求或限定范围的选项>

➡️ 推荐：A，因为 <与项目现状、用户目标或可验证性相关的理由>
```

选项应覆盖真正不同的决策，不要为了凑数量制造细微变体。用户选择后，回写冲突状态和新的明确规则，再检查它是否引发下游冲突。

## 4. 处理过期或互相污染的文档

当文档内容疑似过期时，先用最近的代码、测试、ADR 状态和用户确认判断证据，不要静默删除历史决策。向用户提供至少两个选项：保留并按现状实现，或确认过期后更新/废弃该文档。

如果需要改变 `CONTEXT.md` 的术语，或新增、取代 ADR，调用 Skill tool 运行 `domain-modeling`，按它的 glossary 和 ADR 规则写入。更新多目录 context 时，保持 `CONTEXT-MAP.md` 的指向和范围一致。

文档整理只修改已被确认的内容。不要顺手重写无关章节，也不要把实现细节塞进 `CONTEXT.md`。如果发现文档维护本身是独立的大任务，先列为后续工作，但凡会约束当前实现的冲突仍必须在实现前解决。

## 5. 放行条件

只有同时满足以下条件，才宣布可以开始代码生成或功能实现：

- 需求确认文档中的每个核心行为都有适用的规则来源，或明确记录为本次新决策
- 需求与 `AGENTS.md`、`CLAUDE.md`、ADR、架构规范和测试规范不存在未解决的关键冲突
- 相关 `CONTEXT.md` 的术语与需求使用一致，别名和一词多义已处理
- 疑似过期内容已经确认保留、更新或废弃
- 冲突清单为空，或剩余事项已明确标记为不影响当前实现的非阻塞事项

最终输出一份简短的“实施前冲突检查结果”，包括已解决的冲突、已更新的文档、明确排除的非阻塞事项，以及“可以开始实现”的明确结论。未满足放行条件时，停止在冲突检查阶段，不调用实现流程。
