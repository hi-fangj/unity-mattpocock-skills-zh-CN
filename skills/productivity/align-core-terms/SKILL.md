# 确认核心术语

先处理语言，再处理需求。你的目标不是澄清完整方案，而是让后续访谈使用一套用户认可的术语。

## 工作流程

1. **提取候选术语**

   从用户的原始描述中提取对需求有实际影响的名词、动作、状态、角色、对象和规则名称。保留用户原话作为证据，不要因为表达混乱就自行改写成业务事实。

2. **找出语言冲突**

   标记两类问题：

   - 多个词可能指同一个概念，例如“订单”“购买单”“交易单”。
   - 一个词在不同句子中可能指不同概念，例如“用户”既指登录身份又指业务客户。

   只有会影响后续需求理解的术语才进入确认清单，跳过泛化的技术词。

3. **逐项确认**

   一次只处理一个核心术语或一个紧密相关的术语组。对每项明确询问：

   - **定义**：它具体指什么，不指什么？
   - **范围**：包含哪些情况，排除哪些情况？
   - **歧义**：它是否与其他词同义、重叠或容易混淆？

   如果用户的说法自相矛盾，先指出冲突并给出候选解释，等待用户选择，不要替用户裁决。

4. **维护临时词汇表**

   每次得到回答后，更新一份简洁表格：规范术语、定义、范围、应避免的别名、仍待确认的问题。规范术语应尽量沿用用户已经认可的词，只有在确有必要时才提出新名称。

5. **检查一致性**

   继续确认，直到所有会改变需求含义的候选术语都已解决。检查术语之间是否存在明显的层级、包含关系或生命周期差异；不要把这些关系扩展成尚未确认的业务规则。

## 输出格式

确认过程中使用清晰、可扫描的格式：

```text
🔤 术语 T1：<候选术语>

在你的描述中，<原话证据> 和 <另一处原话> 可能指同一个概念。

请确认：
- 定义：它具体指什么？
- 范围：哪些情况属于它，哪些不属于？
- 歧义：是否与 <相关术语> 区分？是否保留其他说法作为别名？

➡️ 我的暂定理解：<明确标注为暂定，不当作事实>
```

完成后输出“已统一术语”表格，并单独列出“仍未解决的术语”。只有用户确认没有遗漏或需要继续调整时，术语确认阶段才算完成。

## 与后续 Grill 的边界

- 术语确认阶段不追问产品取舍、流程细节、验收标准、异常处理或实现方案，除非回答这些问题是定义术语所必需的。
- 不要把暂定理解写成确定需求，也不要替用户补充不存在的概念。
- 阶段完成时，明确告诉用户可以把已统一的术语连同原始需求交给后续的 `grilling`。如果用户要继续澄清需求，交给用户显式运行 `/grill-me` 或 `/grill-with-docs`。
